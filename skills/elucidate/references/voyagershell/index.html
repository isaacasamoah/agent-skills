Keep the concepts separate

Vessel is the product name for a registered agent or terminal. Code often calls it an instance or session. A record is not a process.

Runtime is the owned app-server or shell process. Frontend is its interactive native client. Terminal is the app that renders it. A registration establishes tracked identity and capture, not ownership of an external process.

Dock is a temporary human control attachment. Rank governs explicit direct assignments. Fleet currently means visual membership. Those are independent relationships.

Agreed release boundary

v0.0 · Look Mum! no hands!

Polish the single-user Voyager that exists: native Vessels, lifecycle, authority, docking, voice, visual Fleets and the private app assistant. Then ship an installable app with its Rust runtime included.

No collaborative harness in v0.0. Prepared Jev rules, collaboration triggers, shared work comparisons, cross-user Fleets and knowledge graph work are deferred to v0.1 or later.

Packaging and native ports support these existing behaviors. They must not become a pretext for a general plugin framework or a rewrite.

Recommendation, not existing infrastructure

One app, bundled native runtime

Use Electron Forge for the first packaging experiment. Electron recommends it, and its packager can include native executable resources. Keep Rust a separate process with the same service contract.

Offer Linux packages, a macOS app in a DMG, and a Windows installer. A package format alone does not establish that docking, voice or lifecycle work on that OS.

Electron packaging · Forge configuration · Native resources

The largest release risk is native portability. The current code depends on Unix sockets and process groups, Linux /proc and PTY operations, X11, and dedicated Ghostty XWayland viewers. Windows cannot build the current service unchanged. macOS also needs native implementations and proof. This is substantive work, not three installer switches.

What opens when a person clicks the avatar icon

Installed Voyager app→Start or reconnect to Rust→Attempt private Codex→Ready panel and available capabilities

This startup sequence already exists in development. Packaging must preserve it using installed resources, without requiring Cargo, npm or a source checkout on the user’s computer.

Use the existing avatar artwork as the icon source, subject to its rights/attribution check. Generate Linux PNG sizes, macOS ICNS and Windows ICO. Give the app one stable application ID and display name.

Resolve executables through process.resourcesPath in the installed app. Keep a deliberate development path only for development. Pass one explicit state location; do not silently move an existing user’s state. Electron resource path.

Run Rust as the current user, detached from UI lifetime. Reopen the app to reconnect, not to spawn duplicates. Quit interface, stop service, remove a Vessel and uninstall remain distinct actions. This proposal adds no root daemon, login-time agent or reboot restoration.

Detect Codex using the actual installed environment or an explicit selected executable. Report installed, authenticated, compatible and unavailable as separate facts. Missing Codex must not prevent the base panel/service from starting. Never bundle account credentials or install/modify Codex silently.

Scope decision

Freeze the release’s actual promise

Agree on a feature checklist from the current branch. Treat existing Fleet deletion semantics and any unsupported adoption claims explicitly. v0.0 may advertise only launch, matching, voice and lifecycle combinations that pass their native checks.

Current source is experiment/private-harness-voice at 771a2f3, not main. Rust currently says 0.2.0 and Electron 0.1.0. Proposed package version is 0.0.0, with product release label v0.0 — Look Mum! no hands!; settle this before tagging.

Done whenThe README, checklist, manifests and release label agree. Isaac has reviewed the source changes before the protected branch or release is updated.
Polish current behavior

Close the user-visible gaps

Exercise the full journey: start service, create Codex/Bash, name and group, open/focus, dock, steer, switch voice, undock, background/reopen, stop and deregister. Check avatar visibility, opacity, menus, sounds, geometry and display scaling.

Resolve Fleet deletion’s requested stop/remove-members behavior once in Rust, or explicitly remove the misleading action from release scope. Preserve past events and show partial failure. Do not let different clients implement different deletion rules.

Done whenEach shipped action has the stated visible effect and an accurate receipt. Unsupported terminal adoption or voice capability is clearly unavailable, without a prepared demo being described as general support.
ETC + DRY

Package one real Linux installation first

Build release-mode Rust binaries and bundle them outside app.asar with Electron Forge. Replace checkout paths with installed resource paths. Establish one installed data-location rule and a service/protocol compatibility check.

Start with Linux x64, RPM and DEB packages as proposed targets. Launch from the application menu on a clean supported machine, without development environment variables. Use the astronaut for the installed launcher icon.

Done whenInstall, click, create, dock and reconnect work without Cargo, npm or a checkout. Paths with spaces, read-only installation, missing Codex and an already-running service all behave correctly.
Orthogonality

Port only the real operating-system boundaries

Separate concrete implementations for local IPC and peer access, process/PTY lifetime, terminal launch, native windows and verified native voice input. Keep authority, operation semantics, Fleet membership and event normalization shared in Rust.

On Windows, evaluate local named pipes restricted to the user and local machine, Job Objects for process ownership, ConPTY and the chosen native terminal. On macOS, evaluate peer-authenticated local transport, native window/accessibility APIs and verified terminal input. These are design candidates until native experiments pass.

Windows shell behavior needs an explicit decision: native PowerShell/cmd adapter, optional Bash environment, or a clearly unavailable shell capability. Ghostty’s Linux flags and the Linux voice PTY mechanism do not port unchanged.

Done whenEach target OS proves the same lifecycle and security meanings through a real native viewer. An unsupported core acceptance criterion blocks that platform’s release; an installer is not a substitute.
Platform delivery

Build and sign the actual downloads

Build Rust and Electron together for each OS/CPU pair on native CI runners. Use Forge makers for Linux packages, macOS DMG/ZIP and a Windows installer. Proposed first matrix is Linux x64, macOS arm64/x64 and Windows x64; do not promise an architecture without a build and native proof.

Sign the app and executable helpers where required. Sign and notarize the macOS bundle; timestamp Windows signatures. Verify the downloaded artifact’s normal launch path and publish checksums. Signing credentials remain in the release environment.

Done whenA fresh machine installs the signed artifact and recognizes the avatar/name. Permissions for microphone, native window control and other required OS access are requested only for their relevant feature.

Data and lifetime

Make reinstall and upgrade behavior explicit

Closing the UI must leave work running. A second launch must reconnect. Updating binaries while the old service owns running agents needs a deliberate compatible-reconnect or user-approved drain/restart path. Never turn saved PIDs into claimed recovered ownership.

Keep history separate from the installed bundle. Back up before schema changes. Define state-file permissions, storage-full behavior and log retention. Uninstall should state what it stops and preserve history unless the person explicitly chooses deletion.

For v0.0, propose manual, user-selected installer updates. No silent replacement or activation of app defaults, prompts, skills or rules. A later update mechanism must preserve the offer-only decision already agreed.

Done whenUpgrade/reinstall preserves the intended state, incompatibility refuses safely, and every restart/loss limit is visible. No automatic task replay, microphone activation or duplicate runtime appears after an uncertain failure.
Native end-to-end proof

Prove the installed app on each platform

Use an installed, authenticated stock Codex with a real task and native terminal. Create a Vessel through the panel, observe its event, dock and speak, launch another Vessel, steer ongoing work, switch the dock and voice, then background/reopen. Stop/remove the trial Vessels and verify capture cutoff with history retained.

Also test missing Codex, unsupported provider version, denied microphone/accessibility permission, disconnected provider, lost UI lease, invalid folder, storage failure and repeated operation ID. Check multiple monitors, scale factors, overlap and opaque terminals.

Done whenSaved outputs, matching successful turn completion, service receipts and native observations support the same claim. Unit tests, screenshots and accepted requests each prove only their own part.
Release review

Prepare the repository and demo for others

Trim prototype-only entry points from the shipped bundle, keep useful probes separate, and document the install, startup, supported matrix, lifecycle, permissions and troubleshooting. Check license attribution, bundled dependencies and native helper contents.

Run repository checks and package smoke tests at the frozen release commit. Have another developer follow installation from the README, then record a demo from a fresh installed app. Include known limits without presenting planned collaboration as present.

Done whenIsaac can trace every demo action to a real service operation and another developer can reproduce the journey without private setup.
Isaac’s release decision

Tag and publish v0.0

After review and Isaac’s approval, merge the accepted changes, tag the chosen release version, attach the verified downloads and checksums, and publish concise release notes under Look Mum! no hands!

Download those published files and repeat the installation/startup smoke test. Carry confirmed defects into a small polish backlog. Start v0.1 collaborative-harness scoping only after v0.0’s review and demos.

Done whenThe published artifact is the one that passed native acceptance, and its supported capabilities and limitations match the documentation.

Why this plan follows the principles

ETC. Package a real slice first. Put changing OS/resource details behind small concrete boundaries. Avoid a framework for integrations that are not yet used.

DRY. Keep the service as the owner of actions and permissions. Derive adapters and release metadata from one explicit contract where useful; do not duplicate lifecycle rules in the installer or UI.

Orthogonality. Installing a desktop client must not move runtime ownership into Electron. Keep app identity, runtime, viewer, capture, rank, Fleet and voice as distinct responsibilities.

What stays out of v0.0

Active collaborative harness, prepared Jev rules, shared work status, cross-user and cross-machine Fleets, knowledge graph construction, secure personal-password provider and tracked native subagents.

General configurable profiles, skill inheritance and rule-update preparation remain design work. They are not prerequisites for packaging the existing app. The earlier configuration proposal remains future design input; this release scope supersedes its suggested next implementation order.
